## 1. Цель и архитектурные ограничения расширения

История банковских операций (`Operation`) отражает только прошлое. Чтобы сервис прогнозировал кассовые разрывы с учётом будущих обязательств и надёжности контрагентов, система расширяется тремя детерминированными модулями:
1. **Единый поток плановых событий (`PlannedEvent`):** учёт заключённых договоров (с разбивкой на предоплату и отсрочку), выставленных/полученных счетов (с контролем просрочки) и предстоящих налогов.
2. **Автоматический налоговый календарь (`taxCalendar.service.ts`):** расчёт обязательных налоговых выплат (ЕНП до 28-го числа, авансы по УСН и НДС по кварталам) с защитой от двойного списания в статистическом ядре.
3. **Универсальный шлюз внешних интеграций и открытых реестров (`integrations-stub` & `counterpartyCheck.service.ts`):** подключение по паттерну Adapter учётных систем (1С), ЭДО, онлайн-касс/маркетплейсов и проверка ИНН по базам ФНС / ЕГРЮЛ / Федресурса (банкротства и блокировки счетов) с прямой математической привязкой к симуляции Монте-Карло.

**Строгие ограничения:**
- Никаких платных внешних API и реальных OAuth-редиректов.
- Никаких LLM/нейросетей в расчётах налогов, скоринга контрагентов и прогноза (100% детерминированный алгоритм с фиксированным seed).
- Строгое соблюдение правила обезличивания данных: полные ИНН и названия контрагентов не сохраняются в БД и не возвращаются в API.

## 3. Расширение модели данных (`server/prisma/schema.prisma`)

1. В существующую модель `User` добавить поле связи:

    plannedEvents PlannedEvent[]

2. Добавить модель `PlannedEvent` строго в следующей редакции:

    model PlannedEvent {
      id               String    @id @default(uuid())
      userId           String
      user             User      @relation(fields: [userId], references: [id])
      type             String    // "contract" | "invoice" | "tax"
      title            String    // Например: "Счет №42 от ООО Ро***" или "ЕНП за 3 квартал"
      amount           Float     // Строго положительное число (> 0)
      direction        String    // "in" | "out"
      expectedDate     DateTime  // Плановая дата платежа (с учётом отсрочки / налогового календаря)
      issueDate        DateTime? // Дата выставления счёта или подписания договора
      deferralDays     Int       @default(0) // Условие отсрочки в днях
      prepaymentPct    Float?    // Процент предоплаты (0..100) для договоров
      counterpartyName String?   // Хранится в маскированном виде, например "Кл***"
      counterpartyInn  String?   // Хранится в маскированном виде, например "77******12"
      counterpartyRisk String    @default("low") // "low" | "medium" | "high" (из открытых реестров)
      source           String    // "1c" | "edo" | "ofd" | "marketplace" | "tax_calendar" | "manual"
      status           String    @default("pending") // "pending" | "paid" | "overdue"
      active           Boolean   @default(true)    // Тумблер учёта на графике прогноза
      createdAt        DateTime  @default(now())

      @@index([userId, expectedDate])
    }

**Правило маскирования при записи:**
Перед сохранением любого `PlannedEvent` (как из ручной формы, так и из импорта 1С/ЭДО) применять функцию обезличивания:
- `counterpartyName`: первые 2 буквы названия + `***` (например, `"ООО Клевер"` $\rightarrow$ `"Кл***"`).
- `counterpartyInn`: первые 2 цифры + `******` + последние 2 цифры (например, `"7701234512"` $\rightarrow$ `"77******12"`).

## 4. Детальная бизнес-логика серверных сервисов (`server/src/services/`)

### 4.1. Логика обработки договоров, счетов и налогов

#### А. Заключённые договоры (`type = "contract"`)
При создании договора (вручную через `POST /api/planned-events` или через синхронизацию) на общую сумму $S$, с датой подписания `issueDate`, условием предоплаты $p\%$ ($0 \le p \le 100$) и отсрочкой $D$ дней (`deferralDays`), сервис автоматически генерирует записи в таблице `PlannedEvent`:
1. Если $0 < p < 100$, создаются **две** независимые записи:
   - **Запись 1 (Предоплата):**
     - `amount`: $\text{round}\left(S \times \frac{p}{100}, 2\right)$
     - `expectedDate`: `issueDate`
     - `title`: `"[Предоплата " + p + "%] " + title`
     - `deferralDays`: `0`
   - **Запись 2 (Постоплата / Окончательный расчёт):**
     - `amount`: $\text{round}\left(S \times \left(1 - \frac{p}{100}\right), 2\right)$
     - `expectedDate`: $\text{issueDate} + D\text{ дней}$
     - `title`: `"[Постоплата, отсрочка " + D + " дн.] " + title`
     - `deferralDays`: $D$
2. Если $p = 0$ или `prepaymentPct == null`, создаётся **одна** запись на полную сумму $S$ с датой `expectedDate` = $\text{issueDate} + D\text{ дней}$.

#### Б. Выставленные и полученные счета (`type = "invoice"`)
- При создании счёта с датой выставления `issueDate` и сроком оплаты `deferralDays` дней поле `expectedDate` вычисляется как $\text{issueDate} + \text{deferralDays}$.
- **Автоматический детектор просрочки (`overdue`):**
  При запросе дашборда (`GET /api/dashboard`) или списка плановых событий (`GET /api/planned-events`) сервер проверяет все записи с `status === "pending"`:
  - Если `expectedDate < today` (начало текущего дня по UTC) и в таблице `Operation` за период `[issueDate, today]` отсутствует операция с тем же направлением `direction`, тем же `counterpartyInn` и суммой `amount` ($\pm 1\%$), статус события автоматически обновляется на `status = "overdue"`.
  - Если событие имеет `status === "overdue"`, оно формирует предупреждение в блоке рисков на дашборде, а его ожидаемая дата в расчётном ядре переносится на $\text{today} + 7\text{ дней}$.

#### В. Налоговый календарь (`taxCalendar.service.ts`, `type = "tax"`)
Реализовать чистый детерминированный сервис `calculateUpcomingTaxes(operations: Operation[], fromDate: Date, horizonDays: number)`, который возвращает массив объектов для записи в `PlannedEvent` (`direction = "out"`, `source = "tax_calendar"`, `counterpartyName = "ФН***"`, `counterpartyInn = "77******00"`):
1. **Единый налоговый платёж (ЕНП — НДФЛ и страховые взносы):**
   - **Срок уплаты:** строго **28-е число каждого месяца**, попадающего в интервал `[fromDate, fromDate + horizonDays]`.
   - **Формула расчёта:** сумма всех операций пользователя с `category === "salary"` и `direction === "out"` за предшествующий календарный месяц, умноженная на коэффициент `0.30` ($30\%$). Если в истории за прошлый месяц операций с категорией `salary` нет, использовать базовую константу из конфига: `65 000 ₽`.
2. **Квартальные налоги (Аванс по УСН 6% и 1/3 НДС):**
   - **Срок уплаты по НК РФ:** **28-е число месяца, следующего за отчётным кварталом** (28 апреля, 28 июля, 28 октября, 28 января).
   - **Формула расчёта:** $6\%$ от суммы всех операционных поступлений (`direction === "in"`, исключая категории/источники `self_loan` и `bank_loan`) за последние 90 дней, уменьшенные на сумму уплаченных страховых взносов (но не более чем на $50\%$).
   - **Гарантия для демо-сценария:** Если при вызове синхронизации налогового календаря (`POST /api/integrations/tax-calendar/sync`) рассчитанная сумма на 28-е число текущего месяца оказывается меньше `150 000 ₽`, система устанавливает детерминированный демо-минимум `180 000 ₽` с названием `"Единый налоговый платёж (ЕНП) и аванс по УСН"`, чтобы гарантированно продемонстрировать кассовый разрыв.

### 4.2. Открытые реестры и скоринг контрагентов (`counterpartyCheck.service.ts`)

Сервис проверяет контрагента по его ИНН (или последним двум видимым цифрам маскированного ИНН) через детерминированный справочник `registry.mock.ts`, имитирующий ответы сервисов ФНС («Прозрачный бизнес»), ЕГРЮЛ и ЕФРСБ (Федресурс / Банкротство).

#### Контракт ответа `CounterpartyCheckResult`:
    export interface CounterpartyCheckResult {
      inn: string;                 // Маскированный ИНН, например "77******12"
      status: "ACTIVE" | "LIQUIDATION" | "BANKRUPT";
      taxDebts: number;            // Сумма задолженности перед налоговой (₽)
      bankruptcy: boolean;         // Наличие активных производств о банкротстве
      riskLevel: "low" | "medium" | "high";
      badgeText: string;           // Короткий текст для UI-бейджа
      detailsText: string;         // Полное описание причины для тултипа и риска
      delayProbability: number;    // Вероятность задержки платежа (0.05 | 0.45 | 0.75)
    }

#### Детерминированная таблица правил классификации ИНН:
1. **Высокий риск (`riskLevel = "high"`):**
   - **Условие срабатывания:** ИНН заканчивается на `"12"`, `"99"` или `"66"` (либо `bankruptcy === true` / `status !== "ACTIVE"`).
   - **Параметры ответа:** `status: "ACTIVE"`, `taxDebts: 480000`, `bankruptcy: true`, `delayProbability: 0.75`.
   - **`badgeText`:** `"Риск неплатежа: стадия банкротства / долг ФНС"`
   - **`detailsText`:** `"Реестр ФНС и Федресурс: задолженность по налогам 480 000 ₽, инициировано дело о банкротстве. Вероятность задержки оплаты — 75%."`
2. **Средний риск (`riskLevel = "medium"`):**
   - **Условие срабатывания:** ИНН заканчивается на `"44"`, `"55"` или `"77"` (либо `taxDebts > 100000` и `bankruptcy === false`).
   - **Параметры ответа:** `status: "ACTIVE"`, `taxDebts: 145000`, `bankruptcy: false`, `delayProbability: 0.45`.
   - **`badgeText`:** `"Долг перед ФНС > 100 тыс. ₽"`
   - **`detailsText`:** `"По данным открытого реестра ФНС числится налоговая задолженность 145 000 ₽. Возможна задержка платежа (45%)."`
3. **Низкий риск (`riskLevel = "low"`):**
   - **Условие срабатывания:** все остальные ИНН (`status: "ACTIVE"`, `taxDebts: 0`, `bankruptcy: false`, `delayProbability: 0.05`).
   - **`badgeText`:** `"Надёжный контрагент (ЕГРЮЛ / ФНС)"`
   - **`detailsText`:** `"Действующая организация, долгов перед налоговой и дел о банкротстве не обнаружено."`

#### Автоматическая генерация риска в таблицу `Risk`:
Когда в систему добавляется входящее плановое событие (`PlannedEvent` с `direction === "in"`) и проверка его `counterpartyInn` возвращает `riskLevel === "high"` или `"medium"`:
- Сервис **обязан автоматически создать запись в таблице `Risk`** (если для этого счёта/договора она ещё не создана):
  - `userId`: `event.userId`
  - `title`: `"Риск задержки оплаты по счёту от " + event.counterpartyName + " (долг перед ФНС / реестр банкротств)"`
  - `type`: `"income_loss"`
  - `amount`: `event.amount`
  - `dateFrom`: `event.expectedDate`
  - `dateTo`: `event.expectedDate`
  - `probability`: `0.75` (для `high`) или `0.45` (для `medium`)
  - `source`: `"auto"`
  - `active`: `true`

### 4.3. Модификация математического ядра прогноза (`server/src/services/forecast.ts`)

В функцию расчёта прогноза `calculateForecast` передаётся дополнительный аргумент `plannedEvents: PlannedEvent[]` (только записи с `active === true` и `status !== "paid"`).

1. **Защита от дублирования налогов (De-duplication Rule):**
   Если в `plannedEvents` есть хотя бы одно активное событие с `type === "tax"` (начисленное налоговым календарём), то при поиске исторических регулярных платежей (`Regular(d)`) все операции из истории с `category === "tax"` **исключаются**. Это гарантирует, что налог на 28-е число будет учтён строго один раз — по точному расчёту из `PlannedEvent`.

2. **Формула детерминированного дневного изменения баланса $\Delta(d)$ на день $d$:**

   $$\Delta(d) = \text{Regular}(d) + \text{IrregularMean}(\text{weekday}(d)) + \sum_{e \in \text{Planned}(d)} \text{Signed}(e) - \sum_{r \in \text{ActiveRisks}(d)} (r.\text{amount} \times r.\text{probability})$$

   где $\text{Signed}(e) = +e.\text{amount}$ при `direction === "in"` и $-e.\text{amount}$ при `direction === "out"`.

3. **Логика прогонов Монте-Карло ($N = 1000$, фиксированный PRNG seed):**
   В каждом прогоне $k \in [1..1000]$ на день $d$:
   - Все исходящие плановые события (`direction === "out"`: налоги, счета поставщиков) списываются со счёта со **100% вероятностью** строго в дату `expectedDate`.
   - Для каждого входящего планового события (`direction === "in"`):
     - Генерируется псевдослучайное число $u \in [0, 1)$.
     - Если у события `counterpartyRisk === "high"` (или есть связанный активный риск с вероятностью $p = 0.75$) и $u < 0.75$, то платёж в этом прогоне **задерживается на 21 день** (переносится с `expectedDate` на $\text{expectedDate} + 21\text{ день}$).
     - В результате на дату 28-го числа (день списания ЕНП) деньги от ненадёжного клиента не успевают поступить, и баланс $B(d)$ опускается ниже порога $T$, фиксируя кассовый разрыв.
